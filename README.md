# urban-os · требования как данные

Интерпретация нормативных требований к получению **свидетельства об утверждении
архитектурно-градостроительного решения** (АГР) объекта капитального строительства
в городе Москве.

## Принцип

**Этот репозиторий не является источником права.** Источник — нормативные акты,
перечисленные в `sources/index.json`. Здесь лежит их *проверяемая транскрипция*:
каждое правило ссылается на пункт первоисточника (`sourceRef`), а каждый
первоисточник — на файл с его sha256.

При расхождении между правилом и первоисточником прав первоисточник, а правило —
дефект транскрипции и чинится выпуском новой версии профиля.

## Раскладка

```
schemas/*.schema.json        формальный контракт формата (3 схемы)
sources/index.json           реестр нормативных источников и внешних органов
sources/files/               сами документы-источники — sha256 сверяется валидатором
sources/snapshots/           неизменяемые снимки источников + указатель baseline
requirements/*.json          корпуса требований (профили), по одному на документ
dictionaries/*.json          справочники: атрибуты IFC, XML-схема ТЭП, разделы формы запроса
deliverables/index.json      что физически должно оказаться в комплекте
monitoring/sources.json      декларативная конфигурация наблюдения
tools/validate.py            целостность реестра + прогон фикстур
tools/check_sources.py       проверка источников, diff, импакт-анализ, утверждение baseline
tools/notify_gitlab.py       создание и обновление GitLab Issue
tools/build_graph.py         граф требований для визуализации во фронтенде
tools/lib/                   extract · normalize · impact · schema · ifc · package · materials
tests/fixtures/*.json        золотые кейсы: контекст → ожидаемые counts
tests/source_fixtures/*.html фикстуры мониторинга, включая негативные
tests/ifc_fixtures/*.ifc     модели для инспектора IFC
tests/package_fixtures/*.json манифесты комплекта запроса
tests/materials_fixtures/*.json манифесты материалов АГР
```

## Правила версионирования

1. **Опубликованный профиль не редактируется.** Исправление любой ошибки, включая
   опечатку, — это новый файл `.v2`. Иначе выданные ранее отчёты становятся
   неповторяемыми.
2. **`selfHash`** в профиле — sha256 его содержимого без самого поля. Считает и
   проверяет `tools/validate.py`.
3. **Проект пинится** на пару `{profileId, version}` и не переезжает на новую
   редакцию сам. Перевод — явное действие с показом дельты.
4. **`status`**: `draft` → `active` → `superseded`. Активной может быть одна
   версия профиля на юрисдикцию и класс модели.

## Типы верификации

| Тип | Кто закрывает | Пример |
|---|---|---|
| `automatic` | движок по `evaluator` | размер ZIP, число треугольников, синтаксис GeoJSON |
| `expert_evidence` | человек с доказательством | нормали наружу, UV без швов, соответствие проекту |
| `external_fact` | внешний документ со сроком | действующий ГПЗУ, выписка ЕГРН |
| `external_verdict` | другое ведомство | заключение Мосгорнаследия, Комитета по туризму |

`automatic` и `expert_evidence` дают терминальное состояние внутри контура.
`external_fact` и `external_verdict` — нет: их нельзя «закрыть экспертизой», можно
только получить или дождаться. В счётчике готовности они считаются отдельно.

## Статус правила `pending_activation`

Часть требований записана в регламенте, но ещё не действует — например,
соответствие результатам цифрового мастер-планирования применяется «после
утверждения алгоритмов в установленном порядке». Такие правила несут
`status: "pending_activation"` и `activationCondition`, не участвуют в подсчёте
терминальности и видны в реестре как предстоящие.

## Мониторинг нормативных источников

Репозиторий хранит интерпретацию. Право живёт снаружи и меняется без нашего ведома.
Мониторинг замечает это изменение и зовёт человека — и на этом останавливается.

```
Официальный источник
      ↓  fetch
Нормализация
      ↓
SHA-256
      ↓
Сравнение с утверждённым baseline
      ↓
Diff
      ↓
Импакт-анализ
      ↓
GitLab Issue
      ↓
Review человеком
      ↓
новая версия профиля requirements
      ↓
новый утверждённый baseline
```

Два правила, которые нельзя нарушить:

> **SOURCE CHANGE ≠ REQUIREMENT CHANGE**
>
> **AUTOMATION DETECTS · HUMAN APPROVES INTERPRETATION**

Автоматика не решает, является ли изменение юридически значимым. Она решает
только, кого и насколько срочно позвать.

### Как это устроено

`monitoring/sources.json` описывает декларативно: откуда брать, как извлекать
содержательную часть, что считать значимым и какие правила затрагивает изменение
каждого раздела.

Страница государственной услуги на mos.ru — React-приложение, но весь контент
лежит в исходном HTML как `window.DATA`. Headless-браузер не нужен: обычный
HTTPS-запрос, `json.JSONDecoder().raw_decode`, каноническая сериализация, SHA-256.

Массивы при нормализации **не сортируются**: порядок пунктов в перечне документов
и в основаниях для отказа семантичен, перестановка — значимое изменение.

### События

| событие | смысл |
|---|---|
| `UNCHANGED` | содержательная часть совпала с baseline |
| `CHANGED` | источник изменился, нужен review |
| `UNAVAILABLE` | источник недоступен (после 3 попыток) |
| `PARSER_ERROR` | ответ получен, но это не та страница — заглушка, капча, другая услуга |
| `BASELINE_MISSING` | baseline ещё не утверждён |
| `BASELINE_STALE` | baseline снят на другой версии извлечения или нормализации |

Нарушение позитивных инвариантов (не тот `TARGET_ID`, нет обязательного раздела,
размер вне коридора) даёт `PARSER_ERROR`, а **не** `CHANGED`. Иначе заглушка WAF
с кодом 200 открыла бы issue «изменился нормативный акт».

### Классификация

| класс | когда |
|---|---|
| `CRITICAL_REVIEW` | затронуто правило `severity: blocker` |
| `REVIEW_REQUIRED` | затронуты правила, но без `blocker` |
| `INFORMATIONAL` | изменение есть, привязанных правил нет |
| `TECHNICAL_FAILURE` | `UNAVAILABLE`, `PARSER_ERROR`, `BASELINE_STALE` |

Правила со статусом `pending_activation` в максимум severity не входят — они
ещё не действуют.

### Snapshots и baseline

`sources/snapshots/<sourceId>/` хранит **сырые** ответы (gzip), именованные по хешу
сырья, и `baseline.json` — указатель на утверждённый снапшот. Снапшот неизменяем.

Имя по хешу сырья, а не нормализованного вида, намеренно: смена версии
нормализатора иначе аннулировала бы всю историю. Сырьё позволяет пересчитать старый
хеш новым кодом, не доверяя новому скачиванию.

**Новый текст не становится baseline автоматически.** Никогда.

### Команды

```bash
# проверить все включённые источники
python3 tools/check_sources.py --report reports/source-check.json

# один источник, без сети, из локальной фикстуры
python3 tools/check_sources.py --source-id msk-284-pp \
    --fixture tests/source_fixtures/mos-v1.html

# утвердить baseline — после того, как человек посмотрел diff
python3 tools/check_sources.py --approve msk-284-pp \
    --snapshot <rawHash12> --by <логин>

# отрендерить тело issue, ничего не создавая
python3 tools/notify_gitlab.py reports/source-check.json --print
```

`--approve` **не ходит в сеть** и работает только с уже сохранённым снапшотом.
Иначе человек утверждал бы контент, которого не видел, и review стал бы декорацией.

### Переменные и секреты

Всё, что нужно пайплайнам этого проекта, живёт в CI/CD-переменных **группы
`ivcorp`**:

<https://gitlab.juralab.ru/groups/ivcorp/-/settings/ci_cd#ci-variables>

Групповые переменные не пересекают границу namespace: значение, положенное в
`juralab`, для пайплайна `ivcorp/*` невидимо. Поэтому и токен раннера
(`IVCORP_RUNNER_TOKEN`), и любые будущие секреты проекта заводятся именно здесь,
а не в общем контуре.

В репозиторий секреты не коммитятся никогда — только имена переменных.

### Автоматизация

GitLab CI в `.gitlab-ci.yml` проверяет целостность данных и тесты на push и в
merge request. Job `source-monitor` запускается по расписанию или вручную, сохраняет
JSON-отчёт как artifact и создаёт GitLab issue только на `CHANGED`. Уведомления
дедуплицируются по `sourceId + previousHash + newHash` среди **открытых** issue.
Job не коммитит requirements и не обновляет baseline.

## Проверка

```bash
python3 tools/validate.py
python3 -m unittest discover tests -v
```

Без зависимостей. Структурная валидация по `schemas/*.schema.json`, затем семантические проверки: ссылочная целостность, уникальность
`id`, соответствие `selfHash`, полноту обязательных полей, применимость
`evaluator` только к `automatic`, и прогоняет фикстуры из `tests/`.

Пересчитать хэши после правки черновика:

```bash
python3 tools/validate.py --rehash
```

## Известные расхождения между источниками

**Ведомость ТЭП против XML-схемы.** Приложение 1 к Регламенту (п. 2.1.11) требует
девять показателей; приложение 5 распоряжения от 16.01.2026 описывает шесть.
Без элемента в схеме остались площадь застройки, абсолютная высота и количество
парковочных мест. Оба документа действующие. Расхождение зафиксировано в
`dictionaries/tep-xml-schema.v1.json` → `crossCheck` и сторожится тестом: сведение
перечней — решение владельца, а не правка реестра.

Провенанс приложения 2 к Регламенту (состав сведений формы запроса) закрыт:
документ лежит в `sources/files/`, его sha256 сверяется на каждом прогоне
валидатора, а 14 правил `form-sec-*` ссылаются на него через `dependsOnSource`.
